# Persistent Core storage and migration dependencies

## Data boundaries

StateCourse is the source of enrollment, content, progress, payment and regulatory records. Its working database remains untouched by this change. `StateCourseReader` uses read-only transactions; the new writer uses a separate, explicitly supplied Core connection pool. The original Measured Decision production backend is not a target either.

The new migration is `storage/supabase/migrations/20261020021909_statecourse_readonly_results.sql`, generated locally with the official Supabase CLI's `migration new` command. It is not added to StateCourse `database/`, root `supabase/migrations/` or the byte-locked upstream history. No migration is automatically applied by the application or CI to any hosted database.

Only an independently approved Core target may receive it. It checks for `public.enrollments` **before creating anything** and refuses if that StateCourse source table exists. Both writer connectors also check the expected database name and absence of that table before writes. Database names alone are not unique Supabase project identities: an operator must independently confirm the actual TLS host/project and credentials before any future application. The separately approved empty StateCourse Core project now exists; it is not linked or enabled by this PR. The [reviewed initial installation package](installation/README.md) fixes its target and constituent hashes; it has now been applied after explicit approval; [APPLIED.md](installation/APPLIED.md) records live verification and remaining advisor blockers.

## Schema

`core_readonly` is private and must not be added to exposed Data API schemas.

| Object | Purpose and enforcement |
| --- | --- |
| `runs` | Server-generated request id; fixed course/enrollment; original actor and organization; unique organization/actor/idempotency key; immutable request identity. Only guarded lifecycle transitions are allowed. |
| `artifacts` | One immutable `snapshot` and one immutable `result` per run. Exact canonical text, database SHA-256 check, valid JSON object, 16 MiB hard bound. Result completion is atomic with result insertion. |
| `events` | Append-only request lifecycle, generated by the run trigger. It records analysis persistence state, not StateCourse operational task history. |

RLS is enabled and forced on all three tables. The non-login, non-inheriting `statecourse_core_store` role has no bypass, superuser, database-creation or role-management authority. Only SELECT/INSERT and the two lifecycle UPDATE columns are granted; no DELETE or artifact/event UPDATE is granted. A preexisting role with unsafe attributes is refused. Artifact/history mutation is rejected by triggers even through the migration owner.

The store opens a transaction, sets the restricted role and transaction-local organization/actor scope, performs parameterized operations, then commits or rolls back and releases the lease. The context comes from server configuration and the verified StateCourse identity, never the request body. RLS is defense in depth for trusted backend SQL; it does not turn a SQL credential into a browser credential. Anonymous/authenticated clients receive no schema access.

Core worker credentials need approved membership in that storage role. The provider worker also needs the existing Core orchestration/budget privileges in its own database. Neither credential belongs in a client or in this repository. Do not reuse a StateCourse source service-role key as the Core writer or assume a table grant bypasses RLS.

## Requests, failures and restart behavior

A new authenticated request reserves its unique key before source capture. Current StateCourse role/MFA authority is checked before any Core write or cache read. Snapshot bytes are committed before the run is marked running and before any provider can be invoked. In provider mode the existing Core repository persists workflows, tasks, attempts, claims, assessments and cost reservations; the API atomically stores the completed explanation and its snapshot binding afterwards.

A completed key returns that exact historical result after restart. A different body under the same key returns 409. An existing reserved/captured/running/interrupted key also returns 409, with no recapture or provider replay; GET returns its status with 202. New keys are deliberate new operations, not retries of an unknown one.

A process crash is not evidence that an HTTP submission failed. Unknown Core attempts retain their budget reservations and remain auditable in the Core tables. The adapter never frees a hold by guessing. A reserved/running wrapper record may remain after a hard crash; automatic lease reclamation, provider resubmission and background runner registration are intentionally absent. Reconcile the actual attempt/hold records before authorizing any subsequent run. If result storage fails after Core completed, the wrapper stays non-replayable; do not rerun providers to manufacture a result.

GET rechecks current StateCourse authority, filters organization and original actor in SQL/RLS, verifies stored hashes/snapshot binding, and returns only the completed explanation/anchors/trace or lifecycle metadata. It neither reruns the analysis nor refreshes source facts. Use a new authorized request when current facts are needed.

## Limits and unverified deployment work

The source keeps its statement timeouts/1000-row bound, observations remain capped at 32, request bodies at 1024 bytes and artifacts at 16 MiB. Provider reservations have configured currency/cost, per-attempt, concurrency, submission-count and wall-clock ceilings. A host still needs cross-replica rate limits and a suitable bounded request duration. The per-key database uniqueness protects duplicate requests across replicas but is not a global spending/rate limit.

Tests exercise actual SQL, RLS/immutability, budget reservations and provider protocols locally, including an actual file-backed database close/reopen. Hosted Supabase advisors, native PostgreSQL concurrency, real credentials/model availability/prices, production privileges, retention/backup operations and deployment are not verified. Data retention/deletion has no API here; any future policy must preserve required audit evidence and be reviewed separately. No business readiness, credit, signoff or launch state changes are claimed.

The exact 79-file initial package and native PostgreSQL rollback/TLS/restart evidence are in [installation/README.md](installation/README.md). Its separate remote schema approval was received and installation was completed; this did not authorize further activation or remediation.
